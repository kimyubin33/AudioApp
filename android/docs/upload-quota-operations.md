# 업로드 용량·건수 제한 운영

기준일: 2026-11-12. SEC-01의 사용자별 업로드 남용 방어를 구현한다.
[출시 체크리스트](google-play-release-readiness.md)와 함께 관리한다.

## 기본값과 설정

| 서버 환경값 | 기본값 | 의미 |
| --- | --- | --- |
| UPLOAD_DAILY_COUNT | 50 | 최근 24시간의 신규 업로드 티켓 수 |
| UPLOAD_DAILY_BYTES | 536870912 | 최근 24시간 예약한 원본 크기 합계, 512 MiB |
| UPLOAD_STORAGE_BYTES | 2147483648 | 사용자별 보관·예약 원본 합계, 2 GiB |

기존 파일당 90 MiB 및 동시 미완료 업로드 10개 제한도 유지한다.
이 수치는 초기 방어 기본값이며 판매 상품이나 사용자에게 약속한 요금제 한도가 아니다.
출시 전 운영 비용·예상 사용량에 맞게 확정한다. 관리자 업로드에도 동일하게 적용한다.

설정은 양의 정수만 허용한다. 건수는 10,000 이하, 용량은 1 TiB 이하이다.
빈 값·음수·소수·잘못된 문자열은 업로드를 503으로 차단한다. 제한을 무제한으로 풀지 않는다.
생략하면 기본값을 사용한다. 운영 변경 시 Worker 설정 배포와 실제 요청 검증이 필요하다.

## 계산 방식과 취소

- 업로드 티켓 생성 전에 선언한 파일 크기를 예약한다.
- SQL의 조건부 INSERT와 DB 트리거가 하나의 원자적 작업으로 티켓·예약을 만든다. 동시 요청도 한도를 넘지 못한다.
- PUT은 선언한 크기·SHA-256을 확인한다. 작은 파일로 예약하고 큰 파일을 보내는 요청을 거부한다.
- 완료 재시도는 예약을 추가하지 않는다. 파일 완료 시 기존 예약이 계속 보관량으로 계산된다.
- 취소·실패한 티켓도 최근 24시간 건수·용량에 포함된다. 취소를 반복해 일일 상한을 우회하지 못한다.
- 취소·실패·만료 상태만으로 공간을 즉시 반환하지 않는다. 기존 시간별 정리 작업이 만료 후 1시간 여유를 두고 R2 삭제를 성공한 뒤 DB 티켓을 삭제하면서 예약을 해제한다.
- 따라서 취소 후 공간 반환은 즉시가 아니며, 통상 티켓 생성 후 약 75~135분에 정리 대상이 된다. 장애·대기열이 있으면 더 늦어진다.
- R2 정리 실패 시 예약과 티켓을 유지한다. 다음 정리에서 재시도한다.
- 반려·공개 중단은 원본 삭제가 아니므로 보관량을 반환하지 않는다. 보관량 초과 시 운영 문의가 필요할 수 있다.
- 예약이 해제된 기록은 최근 24시간이 지난 뒤 정리한다. 완료된 파일은 계속 계산한다.
- 계정 삭제는 기존 R2 삭제 작업을 완료한 뒤 사용자 삭제와 함께 예약 기록을 제거한다.

모든 계산은 사용자 ID 기준이며 자정이 아닌 최근 24시간 구간을 사용한다.
운영자가 DB 티켓을 수동 삭제하면 실제 R2와 계산이 어긋날 수 있으므로 정리 절차를 우회하지 않는다.
버킷에 직접 넣은 파일·소유자를 찾을 수 없는 기존 파일의 전체 비용 관리는 별도 R2 인벤토리 대조가 필요하다.

## API와 사용자 안내

POST /v1/uploads는 한도를 넘으면 티켓을 만들지 않고 429를 반환한다.

| error | 앱·웹 안내 |
| --- | --- |
| limit_reached | 진행 중 요청 제한 / 잠시 후 재시도 |
| upload_daily_count_exceeded | 최근 24시간 업로드 건수 초과, 초안 유지 |
| upload_daily_bytes_exceeded | 최근 24시간 업로드 용량 초과, 파일 크기 확인·초안 유지 |
| storage_quota_exceeded | 보관·예약 공간 초과, 정리 대기 또는 운영 문의 |

일일 제한의 Retry-After는 보수적으로 86,400초다. 정확한 최초 회복 시각을 뜻하지 않는다.
저장량 초과에는 시간만 지나면 해결된다고 안내하지 않으며 Retry-After를 보내지 않는다.
앱은 최대 1 KiB 오류 응답에서 알려진 코드만 해석한다. 임의 서버 본문·내부 오류는 화면에 표시하지 않는다.
실패한 제출의 로컬 초안과 파일은 보존하며 자동 재전송을 반복하지 않는다.

## 마이그레이션과 검증

0010_upload_quota.sql을 0009 다음에 적용한다. 기존 콘텐츠·업로드·신고를 삭제하지 않는다.
기존 원본 크기는 제출 크기와 실제 업로드 크기 중 큰 값을 사용한다.
크기를 확인할 수 없는 기존 파일은 90 MiB로 보수적으로 예약한다.
업로드 행이 없는 기존 R2 콘텐츠도 소유자가 확인되면 이관하며 같은 object_key는 중복 계산하지 않는다.
외부 URL 콘텐츠는 R2 예약에서 제외한다.

운영에서는 백업 후 마이그레이션 → 새 Worker 배포 → 제한·정리 검증 순서로 진행한다.
이전 Worker로 되돌리면 생성 경로의 한도 검사가 사라지므로 운영 중 단순 코드 롤백을 하지 않는다.
쿼터 테이블이나 트리거를 수동 삭제해 제한을 해제하지 않는다.

검증 대상:
- 동시 발급의 건수·저장량 상한, 계정 간 분리, 일일 바이트 경계
- 크기 위조, 취소 반복, R2 정리 실패 후 복구, 24시간 경계
- 완료 재시도·반려·공개 중단의 보관량 유지와 계정 삭제 시 기록 정리
- 기존 데이터 이관과 외래키 유지
- 웹 제한 안내·초안 유지, Rust 오류 코드의 크기 제한·허용 목록

검증 결과: 서버 전체 71개, 웹 E2E 10개, Rust 43개 통과(기존 외부 테스트 1개 ignored).
TypeScript 검사와 Android 빌드·단위 테스트·lint가 성공했다.
로컬 개발 D1에 0010을 적용했다. 운영 DB·Worker 배포는 수행하지 않았다.

## 남은 범위

로그인·검색·신고 조회 등 전체 API 요청 제한, IP/네트워크 단위 방어, 관리자 MFA,
실제 코덱·길이·디코딩 검사와 격리 처리, 비용 경보, 실서비스 부하 검증은 별도다.
이 구현을 실제 미디어 검사나 전체 서비스의 DDoS 방어 완료로 표시하지 않는다.
