저장소: https://github.com/kimyubin33/AudioApp

이 문서는 앱의 목적, 구현 상태, 유료 클라우드 운영안과 남은 작업을 한 파일로 전달하기 위한 자료다.

## 1. 이 앱은 무엇인가

AudioApp은 **이미 만들어진 AI 오디오를 올리고, 검색하고, 듣고, 구독하고, 보관하는 플랫폼**이다.
크리에이터는 외부 도구로 완성한 결과물을 가져온다. 앱의 핵심 가치는 오디오 제작보다 공유·발견·청취에 있다.

첫 출시는 오디오 앱이라는 정체성을 명확히 한다.
피드의 전체·구독, 재생, 보관함, 크리에이터 제출과 검수 흐름에 집중한다.
여기서 구독은 크리에이터를 따라보는 기능이다. 소비자 유료 정기결제 상품이 구현됐다는 뜻은 아니다.

쇼츠·게시글·사진 중심 앨범은 후속 확장 범위다.
관련 기존 코드와 데이터는 남아 있지만, 현재 기본 앱·웹·서버의 공개 제출·노출 범위는 오디오로 제한했다.
이전 기획 문서의 다중 콘텐츠 탭 설명을 이번 출시 범위로 해석하지 않는다.

### 사용자별 핵심 흐름

| 사용자 | 제공하려는 경험 |
| --- | --- |
| 일반 청취자 | 로그인 없이 오디오 탐색·재생, 관심 크리에이터 구독, 저장 목록과 청취 기록 |
| 크리에이터 | + 창작에서 파일·ZIP 가져오기, 원본 미리 재생, 정보·권리 확인, 검수 제출·반려 수정 |
| 운영자 | 크리에이터 권한 관리, 콘텐츠 승인·반려·공개 중단, 신고 검토·처리 이력 |
| 위치 기능 이용자 | 선택적으로 주변 장소와 연결된 오디오 발견 |
| 차량 이용자 | 이동 중 듣기에 집중하는 오디오 경험. 차량 전용 그래픽과 OEM 연동은 별도 단계 |

로그인·권한·최신 약관 수락이 필요한 작업은 서버가 다시 검사한다.
기기 내 보관 목록·청취 기록·프로필은 현재 주요 경로가 로컬 저장이다.
로그인만 하면 다른 기기에 전부 복원되는 서비스로 안내하면 안 된다.

## 2. 어떤 목표와 방향으로 개발했는가

1. **오디오 우선 출시**
   여러 콘텐츠 형식을 한꺼번에 출시하기보다 오디오 발견·재생과 크리에이터 제출의 완성도를 높인다.

2. **간결한 화면, 자세한 제출 과정**
   일반 화면은 글자를 최소화하고 심볼·콘텐츠·재생 동작을 중심으로 구성한다.
   크리에이터 모드는 정확한 원본과 권리를 확인할 수 있도록 일반 화면보다 상세하게 설계한다.

3. **공개 전 확인과 공개 후 대응**
   승인된 크리에이터만 제출하고, 제출물이 바로 공개되지 않도록 한다.
   신고·차단·공개 중단·업로드 권한 회수·계정 삭제를 서비스 기본 기능으로 둔다.

4. **서버가 최종 판단**
   앱의 검사 결과를 신뢰해 권한을 부여하지 않는다.
   소유권, 역할, 동의 버전, 파일 크기·해시, 공개 상태와 용량 한도는 서버가 확인한다.

5. **위치와 차량은 오디오 발견을 돕는 확장**
   위치를 거부해도 기본 탐색·재생이 가능해야 한다.
   지역 캐릭터·이야기, 넓은 오디오 지역, 차량 위치에서 스마트폰 위치로의 전환은 핵심 청취 경험을 보조한다.

6. **운영 가능한 유료 관리형 클라우드**
   개인 PC나 NAS를 상용 서비스의 상시 서버로 사용하지 않는다.
   회사가 계정·결제·접근 권한을 소유하고 공급자의 관리형 서비스를 이용한다.

추천 알고리즘의 세부 설계는 동업자 담당이다.
현재 위치 탐색·카탈로그·재생 기반이 있다는 사실을 개인화 추천 모델 완성으로 표현하지 않는다.

### 차량 디자인의 정확한 상태

먹물이 물에 퍼지는 듯한 화면과 입체적 움직임은 차량용 시각 경험을 탐색하는 프로토타입이다.
현재 debug용 Ink Studio·AAOS 에뮬레이터 검증은 실제 현대차 내비게이션 탑재를 뜻하지 않는다.
실차 위치 API, 내비게이션 옆 패널 배치, 차량↔폰 위치 전환, OEM 계약과 운전 중 표시 범위는 미완료다.
차량 플랫폼이 허용하는 미디어 UI와 OEM 전용 화면을 구분해 별도 개발·검증해야 한다.

## 6. 기업 구독형 서버 운영안

### 권장안

**회사 소유 Cloudflare 계정에서 Workers Paid + D1 + 비공개 R2를 운영하고,
미디어 검사에만 별도의 관리형 컨테이너 작업 서비스를 붙이는 구성을 권장한다.**

현재 백엔드가 이 구성으로 작성되어 있어 운영 연결에 집중하기 좋다.
이는 현재 코드와 팀 상황에 근거한 설계 제안이며, 계약·구매·운영 배포가 완료됐다는 뜻은 아니다.

여기서 “기업 구독형”은 회사가 결제하는 관리형 클라우드를 의미한다.
사용자의 앱 유료 구독 기능과는 별개다.
월 정액 무제한 전용 서버를 뜻하지도 않는다.

Workers Paid는 기본 구독료에 요청·CPU 사용량에 따른 과금이 더해지는 구조다.
Cloudflare 웹사이트용 Pro/Business 요금제와 Workers 요금제는 별개다.
정식 Enterprise 요금·지원 범위는 계약을 확인해야 한다. [Workers 과금 안내](https://developers.cloudflare.com/workers/platform/pricing/)

| 구성 | 역할 | 상태 |
| --- | --- | --- |
| Workers Paid | 앱/웹 API, 인증·권한·공개 상태 검사 | 코드 있음, 운영 연결 필요 |
| D1 | 계정·콘텐츠·업로드·신고·동의·검수 이력 | 코드 있음, 운영 DB 필요 |
| R2 비공개 버킷 | 원본 오디오 보관 | 코드 있음, 운영 버킷 필요 |
| Workers 정적 자산 | 크리에이터·관리자·삭제 요청 웹 | 코드 있음, 공개 도메인 필요 |
| 회사 IdP/MFA + Access 등 | 관리자 화면과 관리자 API 추가 보호 | 설계·구현 필요 |
| 작업 큐와 실패 큐 | 미디어 검사 요청·재시도·누락 방지 | 신규 구현 |
| 관리형 컨테이너 작업 | ffprobe·FFmpeg 전체 디코딩 검사 | 신규 구현 |
| 로그·경보·백업 | 장애·비용·삭제 지연 감시, 복구 | 운영 구성 필요 |

R2는 저장량과 작업 횟수에 과금하고 인터넷 전송량 자체의 egress 요금은 별도로 부과하지 않는다.
하지만 API 호출·DB·검사 실행·로그까지 무료라는 뜻은 아니다. [R2 과금 안내](https://developers.cloudflare.com/r2/pricing/)

D1은 읽기·쓰기·저장량 기준 비용과 단일 DB 크기 제한이 있다.
초기 메타데이터 저장에는 현재 구조를 사용하되 추천 이벤트를 무제한으로 같은 DB에 누적하지 않는다.
실제 데이터·쿼리 부하가 한계에 접근하면 이벤트 저장 분리와 관리형 PostgreSQL 등 이전을 검토한다.
[D1 과금](https://developers.cloudflare.com/d1/platform/pricing/), [D1 제한](https://developers.cloudflare.com/d1/platform/limits/)

### Enterprise 계약이 필요한 경우

회사에서 지원 응답 시간, SLA, 계약상 보안·감사 요구, 처리 지역, 구매·정산 절차를 먼저 정한다.
그 조건이 표준 유료 서비스로 충족되지 않을 때 공급자에게 Enterprise 견적을 요청한다.
이 문서만으로 특정 SLA나 국내 데이터 상주를 보장하지 않는다. 실제 계약·리전·처리 흐름을 확인해야 한다.

월 비용을 완전히 고정하고 싶다면 예상 사용량·초과 요금·예산 상한·장애 지원을 포함한 견적이 필요하다.
공급자를 바꿔야 하는 경우에는 코드 이전 범위와 운영 부담까지 비교한다.
첫 출시에서는 단순히 “기업용”이라는 이유만으로 이미 구현한 API 전체를 재작성하지 않는 것을 권장한다.

### 비용 산정에 필요한 입력

- 월간/일간 사용자 수, 평균 청취 시간, 원본 평균 크기와 보존 기간.
- 일일 업로드 건수, 검사에 필요한 CPU 시간·실패 재시도 횟수.
- Range 요청 수, 검색·추천 요청 수, DB 읽기·쓰기 수.
- 원본 외 변환본·백업본·로그의 저장량.
- 운영자 수, 보안 서비스·유료 지원·도메인 비용.

예: 128 kbps 오디오 20분은 약 19.2 MB이고, 이런 원본 1만 개는 약 192 GB다.
원본만 계산한 산술 예이며 실제 요금 견적은 아니다.
월 비용은 기본 구독료 + 초과 요청/CPU + DB + R2 저장/작업 + 검사 작업 + 보안/관측 비용으로 계산한다.
예산 알림만 설정하면 지출이 자동 중단된다고 가정하지 말고, 서비스 한도·업로드 중단 절차를 함께 둔다.

## 7. 백엔드에서 무엇을 어떻게 완성할 것인가

아래 단계는 후속 개발 계획이다. 새 작업 큐·미디어 검사·MFA가 이미 연결된 것으로 해석하지 않는다.

### 7.1 운영 환경 분리와 배포

1. 회사 명의 계정·도메인·결제·소유권을 설정하고 개인별 관리자 계정을 발급한다.
2. 개발·staging·production의 Worker, D1, R2, Google OAuth를 분리한다.
3. 현재 wrangler.toml의 영(0)으로 된 D1 ID를 실제 환경별 바인딩으로 교체한다.
4. 별도 테스트 DB에서 0001~0010 순서의 마이그레이션을 적용하고 기존 데이터 보존·복구를 검증한다.
5. TOKEN_SECRET 등 비밀값은 공급자의 비밀 관리 기능으로 넣는다. 앱·Git·전달 ZIP에 넣지 않는다.
6. production의 DEV_MODE와 ENABLE_EXTENDED_FORMATS는 비활성화한다.
7. 공개 HTTPS API, /creator, /admin, /delete-account, 실제 정책 URL을 연결한다.
8. 앱의 releaseApiBaseUrl·googleWebClientId를 설정하고 실제 Google 계정으로 전 과정을 검증한다.
9. 운영 배포는 CI의 승인 단계, 마이그레이션 기록, 배포 버전과 복구 계획을 남긴다.
10. 0011 이후 마이그레이션은 기존 콘텐츠를 모두 validation_status=pending으로 만든다. 공개 콘텐츠가 있는 DB에 적용하기 전에 재검사 계획을 세운다.

현재 운영 리소스가 외부에 이미 있을 수 있으나 이 작업에서는 확인하지 않았다.
로컬 DB를 reset하거나 개발 샘플을 운영 DB에 넣어서 준비를 대신하지 않는다.

### 7.2 실제 미디어 검사 파이프라인

현재 서버는 크기·해시·최소 헤더를 검사한다.
다음 단계에서는 일반 API 요청 안에서 긴 디코딩을 수행하지 않고 별도 작업으로 분리한다.

목표 흐름:

```text
앱/웹 업로드
  → 비공개 R2 원본
  → 검사 작업 등록
  → 격리된 컨테이너에서 전체 검사
  → 검사 성공 + 운영자 승인
  → 공개 목록·재생
```

구현 순서:

1. 콘텐츠 검수 상태와 별도로 validation_status, job_id, 원본 SHA-256/객체 식별, 시도 횟수, 실패 코드, 검사 버전을 저장한다.
2. 업로드 완료와 작업 원장을 같은 DB 트랜잭션으로 기록한다. 발행 대기 원장을 두고 큐 발행 실패를 재시도한다.
3. 큐에는 임의 외부 URL 대신 서버가 정한 콘텐츠·원본 식별자를 전달한다.
4. 컨테이너는 허용된 R2 원본만 받아 파일 크기·해시를 다시 확인한다.
5. ffprobe로 컨테이너·트랙·코덱·길이를 확인하고 FFmpeg 등으로 전체 디코딩한다.
6. 오디오 트랙 존재, 허용 코덱, 영상 트랙 금지, 최대 길이·손상·과도한 자원 사용을 검사한다.
7. 프로세스는 비관리자 권한, CPU·메모리·임시 디스크·실행 시간 제한, 최소 네트워크/스토리지 권한으로 실행한다. 라이브러리 패치와 라이선스도 관리한다.
8. 결과는 인증된 서버 경로로만 반영한다. 현재 원본 식별자·검사 버전이 맞는 경우에만 상태를 변경한다.
9. 검사 통과 전에는 일반 공개와 미디어 제공을 차단한다. 관리자 미리 재생도 검사 완료를 확인한 뒤 허용하도록 수정한다.
10. 승인 API·CLI·목록·상세·미디어·추천이 같은 검사 조건을 지키도록 한다. 운영의 외부 URL 콘텐츠도 검사 우회로가 되지 않게 한다.

Cloud Run Jobs는 컨테이너 작업을 실행하고 종료하는 관리형 후보이며 시간 제한·재시도를 설정할 수 있다.
이는 신규 구성 후보이고 현재 코드에 연결되어 있지 않다. [Cloud Run Jobs](https://docs.cloud.google.com/run/docs/create-jobs)

Cloudflare Queues를 쓰면 중복 전달을 전제로 작업 ID 기반 중복 실행 방지와 완료 결과의 재적용 방지가 필요하다.
[Queues 전달 보장](https://developers.cloudflare.com/queues/reference/delivery-guarantees/)
큐에서 컨테이너 실행 API로 연결하는 서비스 인증·최소 권한·작업 상태 조회도 별도로 구현한다.
긴 수명의 클라우드 관리자 키를 앱이나 큐 메시지에 넣지 않는다.

실패 처리는 검사 실패·일시 장애·시간 초과를 구분한다.
재시도 상한과 실패 큐, 수동 재처리 기록을 두고 검사 실패를 운영자가 단순히 승인으로 덮어쓰지 못하게 한다.
탈퇴·원본 삭제와 검사가 겹치면 종료된 작업이 콘텐츠를 다시 공개하지 못하도록 한다.

현재 관리 CLI는 보존된 확장 형식도 승인할 수 있다. 기본 공개 API의 오디오 제한과 CLI 입력 제한은 같지 않다.
운영자는 CLI로 비오디오를 승인하지 않으며, 후속 작업에서 CLI 승인 정책도 운영 공개 범위와 맞춘다.
현재 공개 목록·상세·미디어 경로의 오디오 제한은 서버에서 별도로 적용한다.

### 7.3 전체 요청 제한과 관리자 보안

- 기존 업로드/신고 한도 외에 로그인, 검색, 주변 탐색, 상세, 파일 전송, 관리자 조작의 요청 제한을 추가한다.
- 공개 API는 네트워크 단위 방어와 서버 측 제한을 함께 사용한다. 계정별 엄격한 용량 제한은 기존 DB 원자성을 유지한다.
- 관리자 MFA는 회사 IdP와 접근 제어를 연결한다. /admin HTML만 보호하고 /v1/admin API를 열어두지 않는다.
- Access 등을 적용할 경우 서버에서도 인증 토큰의 발급자·대상·서명·만료를 검증하고 기존 admin 역할 검사도 유지한다. [Access JWT 검증](https://developers.cloudflare.com/cloudflare-one/access-controls/applications/http-apps/authorization-cookie/validating-json/)
- 개발용 호스트·직접 Worker 주소가 관리자 인증 우회 경로가 되지 않도록 제한한다.
- 로그아웃·권한 회수·계정 정지 시 세션 무효화 범위와 토큰 교체 절차를 정한다.
- 공유 관리자 계정을 쓰지 않고 접근·권한 변경·심사 이력을 개인별로 남긴다.

### 7.4 신고·계정·정책 운영

- 전체 계정 정지/복구와 업로드 권한 회수를 구분한다.
- 접수·검토·조치·통지·이의제기·재심의 상태와 담당자를 정한다.
- 신고자에게 보이는 처리 사유와 내부 운영 메모를 구분하고 불필요한 개인정보를 노출하지 않는다.
- 이의제기는 접수 번호·제출 시각·재심 담당·결과를 기록하고 운영 이메일 또는 앱 경로로 연결한다.
- 삭제 cron의 미처리 건수·최장 지연·재시도 실패를 감시한다. 담당자가 실패를 확인할 수 있어야 한다.
- 보존 대상과 기간, 삭제 완료 기준, 법적 보존 예외는 회사가 확정한다.
- 실제 약관·개인정보·크리에이터 정책·문의처와 POLICY_VERSION을 연결한다.

이용약관 수락, 사용자/콘텐츠 신고·차단과 지속적인 검토가 필요한 서비스다.
신고 버튼이 존재한다는 것만으로 운영 대응까지 완료된 것은 아니다.
[Google Play UGC 정책](https://support.google.com/googleplay/android-developer/answer/9876937?hl=ko)

### 7.5 추천 알고리즘 — 동업자 담당

추천 품질 실험과 공개 권한 검사를 분리한다.
알고리즘이 어떤 점수를 주더라도 승인·검사 통과·미삭제 콘텐츠만 후보가 되어야 한다.

첫 연결은 정교한 개인화보다 승인된 최신/인기 오디오와 구독 기반의 단순 기준으로 시작할 수 있다.
“인기”는 실제 집계 기준이 준비된 뒤 사용하고 임의 데이터를 실제 인기 순위로 표시하지 않는다.

설계할 항목:

- 취향·장르·길이·구독·현재 청취 상황 등 입력과 이용 목적.
- 노출·재생 시작·일정 시간 청취·완주·건너뛰기 등의 이벤트 정의.
- 중복 이벤트, 반복 재생, 스팸·조회수 조작 방어.
- 차단·신고·공개 중단·탈퇴의 즉시 반영과 추천 장애 시 기본 목록.
- 신규 사용자·신규 콘텐츠의 초기 추천과 평가 기준.
- 이벤트 보유 기간·사용자 연결·동의 또는 다른 처리 근거·철회/삭제.
- 차량 환경에서는 운전 중 조작을 줄이고 플랫폼이 허용하는 재생 기능에 맞추기.

예를 들어 /v1/recommendations와 이벤트 수집 API를 추가할 수 있으나 이는 제안 이름이며 현재 완성 API가 아니다.
현재 청취 기록은 주로 로컬 저장이므로 서버가 이미 개인화 학습 데이터를 충분히 가지고 있다고 가정하지 않는다.
위치 개인화는 명시적인 선택과 실제 필요한 정밀도·보유 범위를 먼저 결정한다.

### 7.6 관측·백업·부하·비용

- API 오류율·지연, R2 실패, 검사 대기 시간, 신고/삭제 지연, DB 용량·쿼리 비용을 감시한다.
- 토큰·업로드 서명 URL·신고 본문·정밀 좌표를 오류 로그에 그대로 남기지 않는다.
- D1 복구와 R2 원본 보존을 따로 검증하고 별도 테스트 환경에서 실제 복원한다.
- 목표 복구 시간(RTO)과 허용 데이터 손실(RPO)을 운영 담당자가 정한다.
- Range 재생·동시 재생·느린 회선·재생 중 공개 중단을 부하 테스트한다.
- 캐시를 추가하면 승인 회수·삭제 반영 시간을 명시하고 검증한다.
- 월 예산 경보, 신규 업로드 중단, 검사 동시성 제한, 장애 연락망을 준비한다.

| 4 | 미디어 검사·요청 제한·관리자 보안 | 백엔드 | 손상 파일 거부, 중복 작업 안전, MFA 우회 차단 |
| 5 | 신고·삭제·문서·백업·경보 운영 | 운영/백엔드 | 신고 처리, 삭제 실패 복구, 백업 복원 실습 기록 |
| 6 | 추천 기본 연결과 평가 | 동업자/백엔드 | 후보 권한 필터와 장애 시 대체 목록 테스트 |
| 7 | 서명 AAB·실기기·Play 내부/비공개 테스트 | Android/QA | 서명 정보, 테스트 결과, Console 등록 |
| 8 | 공개 출시 판단 | 공동 창업자/운영 | 남은 차단 항목 해소와 출시 승인 기록 |

날짜와 비용은 담당자·월 예산·계약 조건을 확인한 뒤 잡는다.
오디오 공개 출시와 OEM 차량 연동을 같은 완료 조건으로 묶지 않는다.

## 9. Play 스토어에 올리기 전에 반드시 확인할 것

현재는 로컬 debug 성공을 확인한 상태다. 아래 조건을 충족한 서명 빌드가 필요하다.

- [ ] 공개 HTTPS 운영/테스트 서버 연결과 개발용 인증 비활성화.
- [ ] 실제 Google 로그인, 승인 크리에이터 제출, 검수, 공개 청취를 외부 네트워크에서 검증.
- [ ] 실제 이용약관·개인정보처리방침·크리에이터 정책·지원 연락처 공개.
- [ ] 앱 안과 웹의 계정 삭제가 실제 관련 데이터 정리로 이어지는지 확인.
- [ ] 신고·차단·운영 검토와 조치 담당·기준 마련.
- [ ] 업로드 키, Play App Signing, versionCode 관리와 서명된 release AAB 검증.
- [ ] Rust/JNA 및 모든 네이티브 라이브러리의 16KB 호환성과 실제 해당 환경 실행.
- [ ] 현재 제출 정책에 맞는 target API, 권한·포그라운드 서비스 선언 확인.
- [ ] 개인정보·SDK·인프라 수집 현황을 반영한 Data safety 작성.
- [ ] 대상 연령·콘텐츠 등급·광고 여부·심사 접근 방법·스토어 설명/이미지 확정.
- [ ] 잠금화면 장시간 청취, 전화·다른 앱 오디오 포커스, Bluetooth, 통신 단절, 앱 재시작, 접근성 테스트.
- [ ] 해당 계정에 적용되는 내부/비공개 테스트와 프로덕션 액세스 요건 충족.

계정 생성 기능이 있는 앱은 앱 내부 삭제 경로와 웹 삭제 요청 경로가 필요하다.
현재 경로 코드는 있지만 공개 운영 주소와 실제 처리 검증이 남아 있다.
[계정 삭제 요구사항](https://support.google.com/googleplay/android-developer/answer/13327111?hl=ko)

개인정보처리방침과 데이터 보안 답변은 실제 앱·SDK·서버 동작에 맞춰 작성한다.
국내 사업자·위치·국외 이전·보존 기간 관련 검토도 실제 계약과 서비스 대상에 맞춰 진행한다.
[Google Play 사용자 데이터 정책](https://support.google.com/googleplay/android-developer/answer/10144311?hl=ko)

2023년 11월 13일 이후 생성한 신규 개인 개발자 계정에 해당하면
최소 12명의 테스터가 14일 연속 참여하는 비공개 테스트 등의 요건이 적용된다.
회사 계정인지와 실제 Console에 표시되는 요건을 확인한다.
[개인 개발자 테스트 요건](https://support.google.com/googleplay/android-developer/answer/14151465?hl=ko)

이 앱에는 네이티브 라이브러리가 있으므로 단순 targetSdk 설정만으로 16KB 대응 완료를 판단하지 않는다.
[Android 16KB 지원 안내](https://developer.android.com/guide/practices/page-sizes)

## 10. 동업자에게 실제로 전달하는 방법

### 소스 전달

1. 변경 파일과 미추적 파일을 검토해 최신 앱·Rust·서버·마이그레이션·테스트·문서를 같은 인수인계 커밋으로 고정한다.
2. 비공개 협업 권한을 확인한 Git 저장소 또는 그 커밋의 소스 아카이브로 전달한다.
3. .scratch, 빌드 출력, 로그, .dev.vars, local.properties, 인증서 개인키, 업로드 키, 운영 DB·사용자 파일을 포함하지 않는다.
4. .gitignore에 의해 제외된 생성 라이브러리·UniFFI 바인딩은 재생성 절차를 안내한다.
5. 새 clone에서 서버 테스트·Rust 빌드·Android 빌드를 실행한 결과를 전달한다.

소스 전체 폴더를 무조건 ZIP으로 압축하거나 git add .로 일괄 추가하지 않는다.
이번 구현은 커밋에 포함했다. 다음 전달에서도 git archive는 지정한 커밋만 담으므로 이후 미커밋 변경까지 포함한다고 가정하지 않는다.
프로젝트 소유권과 외부 의존성·이미지/음원·로고의 이용 권한도 인수인계 시 확인한다.

### 실행 안내

필수 도구는 Android Studio·SDK 37·Android NDK·Gradle 실행 JDK 25, Rust 및 Android 타깃,
cargo-ndk, Python 3, Node/npm, Git이다. Gradle Wrapper는 9.6.0이며 앱 소스의 Java 11 호환 설정과 실행 JDK는 별개다.
Android Rust 타깃은 arm64-v8a·armeabi-v7a·x86_64용을 준비한다. 버전은 Gradle·Cargo·package lock 파일에 맞춘다.

대표 검증 명령은 아래와 같다. 각 명령은 명시된 디렉터리에서 실행한다.
비밀 설정은 .dev.vars.example을 참고해 수신자가 따로 만든다. 기존 설정을 덮어쓰지 않는다.
이번 검증 환경은 Node 24.15.0 / npm 11.12.1, rustc·cargo 1.99.1이다.
서버 테스트는 node:sqlite와 TypeScript 직접 실행을 사용하므로 오래된 Node로 실행하지 않는다.
Windows E2E는 설치된 Microsoft Edge(msedge), 다른 OS에서는 Playwright Chromium을 사용한다.
검증 명령 전에 npm.cmd run types로 생성 타입을 준비한다.

| 디렉터리 | 명령 | 목적 |
| --- | --- | --- |
| server | npm.cmd ci | lock 파일 기준 의존성 설치 |
| server | npm.cmd run types | Git에서 제외된 worker-configuration.d.ts 생성 |
| server | npm.cmd run db:migrate | 로컬 개발 DB 마이그레이션 |
| server | npm.cmd run check | TypeScript 검사 |
| server | npm.cmd test | 서버/웹 단위·통합 테스트 |
| server | npm.cmd run web:test | 브라우저 E2E, Playwright 브라우저 준비 필요 |
| audio-core | cargo test --locked | Rust 테스트 |
| 저장소 루트 | python scripts/build_android.py | Android Rust 라이브러리·Kotlin 바인딩 생성 |
| android | .\gradlew.bat :app:testDebugUnitTest :app:lintDebug :app:assembleDebug | Android 개발 빌드 검증 |

로컬 실행은 server 디렉터리에서 npm.cmd run dev, 별도 터미널의 저장소 루트에서
python dev-server/tls_proxy.py를 실행해 개발 CA를 생성·debug 리소스에 복사한 뒤 Android 앱을 빌드·설치한다.
인증서 생성에는 OpenSSL이 필요하다. 이미 CA 없이 빌드한 debug 앱은 다시 빌드해야 한다.
위 표의 Android 빌드는 로컬 TLS 준비 후 실행하고, Android 에뮬레이터로 연결한다.
운영 검증에 이 개발용 가짜 로그인·인증서를 사용하지 않는다.
db:reset은 기존 개발 데이터를 지우는 작업이므로 일반 인수인계 절차에 넣지 않는다.

### 체험용 파일과 출시 파일

- 체험용 APK: 공개 테스트 서버에 연결되는 서명 빌드, 테스트 계정 사용법, 알려진 제한을 함께 제공.
- 출시용 AAB: 운영 주소·서명·정책·검증이 완료된 별도 산출물.
- 어느 파일이든 앱 버전, 소스 커밋, 연결 환경, 테스트 날짜를 표시.
- 비밀키를 APK/AAB와 함께 전달하지 않고 회사의 별도 비밀 관리 경로로 관리.
